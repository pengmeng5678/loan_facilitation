# 项目四：助贷对话数据中台

> 代码：`src/data_platform/` ｜ 接口前缀：`/data` ｜ 测试：`tests/test_data_platform.py`
> 一句话定位：**把微信原始聊天记录加工成可训练、可检索、可考核的数据资产**，成为其他 AI 项目的数据源头。

---

## 一、它解决什么问题

助贷公司最值钱的数据是**业务员和客户几年的真实微信聊天记录**：真实需求、真实异议、真实成交路径都在里面。但这些数据以最脏的形态存在（微信本地 SQLite）：

| 问题 | 具体表现 | 不做的代价 |
|---|---|---|
| 采不出来 | wxid 不是人名、群消息要还原发送者、时间单位有秒有毫秒 | 数据"看得见用不了" |
| 不能直接用 | 手机号、身份证、银行卡、真实报价混在里面 | 直接训练 = 泄露客户隐私与公司底价 |
| 质量分层缺失 | 系统消息、表情、单字应答、推销占绝大多数 | 灌进向量库只会让召回变差 |
| 无单一可信源 | 各项目各自导数据、各自清洗 | 口径分裂、脱敏遗漏、成本重复 |
| 用不回 | 样本用完就散 | 模型没法持续变好 |

数据中台的价值就是四个"一次"：**清洗一次、脱敏一次、审核一次、多下游复用**。

---

## 二、数据流（四层，每层职责单一）

```
微信本地 SQLite（message + rcontact）
   │  ① 抽取：wxid→显示名 / 群消息发送者还原 / 消息类型占位 / 时间单位归一
   ▼
raw_messages            原始层（不可变，只增不改）
   │  ② 清洗：9 级分类 → 三层脱敏 → 5 分钟窗切块 → 同角色合并 → 去重
   ▼
conversation_blocks     清洗层（含分类/质量分/QA/敏感标记）
   │  ③ 审核：pending → approved / rejected / edit（人工闸门）
   ▼
staging_conversations   审核层（唯一可信数据源的载体）
   │  ④ 复用：四格式导出 + 向量切片 + 结构化文章
   ▼
exports / knowledge_chunks / knowledge_articles
```

八张表对应八个事实，每张都回答一个具体问题：

| 表 | 回答的问题 |
|---|---|
| `raw_messages` | 原来是什么样（能否回溯） |
| `conversation_blocks` | 清洗逻辑跑出了什么（含被丢弃的块与原因） |
| `staging_conversations` | 哪些数据被批准用于下游 |
| `review_audit` | 谁在什么时候批了什么（可审计） |
| `exports` | 这批模型是用哪批数据训的（含内容哈希） |
| `knowledge_chunks` | 检索命中的是原始对话的哪一段 |
| `knowledge_articles` | 话术/场景从哪条对话提炼的 |
| `ingest_batches` | 每次清洗的输入输出规模 |

## 三、五个关键设计决策（面试重点）

### 决策 1：脱敏必须幂等，且规则有优先级

**身份证必须先于银行卡**：18 位身份证同时满足"16-19 位连续数字"，先跑银行卡规则会把它打成四不像，审计里记录的类型还是错的。所以候选命中按 `priority` 排序、重叠时高优先级胜出，而不是靠正则写法碰运气。

**幂等性是三层冗余脱敏的前提**：同一段文本跑两次，第二次必须零命中（`verify()` 返回空）。否则"三层"不仅没兜底，还会把文本越改越乱。导出层每次都会调 `verify()`，非空就整批拒绝导出——这让"我们做了三层脱敏"变成**可执行、可检验**的断言，而不是一句口号。

三层分别落在：`clean`（成块时）/ `write`（入库与人工编辑时）/ `export`（导出时）。

### 决策 2：分类与"能否训练"是两个开关

敏感对话（投诉/维权/催收）**必须进暂存区**——主管要看到投诉苗头；但它的 `dataset_eligible=False`，**永远不进训练集**。

把这两件事合成一个布尔值，是这类系统最常见的合规漏洞：要么主管看不到风险，要么投诉被包装成营销案例（后者是事故，不是瑕疵）。

### 决策 3：审核闸门只允许三条边，且编辑即重置

```
pending  → approved   批准（可导出）
pending  → rejected   驳回
approved → rejected   撤销（必须写理由）
```

- **幂等**：重复提交同一个 block 返回已存在那条且不改状态——重跑清洗不能把已批准的数据打回 pending，否则下游导出会突然少数据；
- **重复 approve 不加审计行**；
- **编辑即重置**：新 revision + 回到 pending，并**重新跑脱敏与分类**——人工编辑是最容易把手机号/价格又贴回去的环节，不能信任"人不会贴错"；
- **非法流转直接报错**，不做善意猜测。

### 决策 4：导出幂等（同输入同输出）

文件名与 `export_key` 都由内容哈希派生：

```
content_hash = sha256(格式化的全部行)
export_key   = sha256(format | watermark | content_hash)
```

重复导出同一批数据直接复用已有文件（`reused=True`）。下游不会因为"又点了一次导出"拿到两份不一样的数据，模型训练也能复现"这批数据长什么样"。

### 决策 5：LLM 只做语言层，且必须有规则兜底

- 分类、脱敏、切块、质量分、场景判定：**全部确定性规则**；
- LLM 只用于"从对话里提炼结构化知识"这一层语言任务；
- 模型输出要校验（字段齐、非空、置信度合法），**校验不过就走规则兜底**（从已抽好的 QA 对里取一条），并在 `extractor` 字段如实标注 `llm` / `rule`。

理由：如果模型抖动就丢样本，知识库会"时多时少"，下游无法复现。宁可置信度低一点，也不能让管线不可用。

## 四、9 级分类与质量分

| 优先级 | 分类 | 是否进暂存 | 可训练 |
|---|---|---|---|
| 1 | 系统消息 | ✗ | ✗ |
| 2 | 媒体消息（图片/语音/文件占位） | ✗ | ✗ |
| 3 | **敏感对话**（投诉/维权/催收/监管） | **✓** | **✗** |
| 4 | 垃圾广告 | ✗ | ✗ |
| 5 | 过短 | ✗ | ✗ |
| 6 | 闲聊 | ✗ | ✗ |
| 7 | 重复 | ✗ | ✗ |
| 8 | 普通有效 | ✓ | ✓ |
| 9 | 高价值 | ✓ | ✓ |

**敏感(3) 刻意排在过短(5) 之前**：一条两个字的消息可能就是投诉苗头，风险不能因为"字少"被漏掉。

质量分（0-1，权重显式可配）：

| 信号 | 权重 | 理由 |
|---|---|---|
| 轮次 | 0.25 | 谈得越深信息越多 |
| 业务词覆盖 | 0.25 | 真的在聊业务而不是寒暄 |
| QA 对数量 | 0.20 | 能直接变成问答/陪练素材 |
| 业务侧字数 | 0.20 | 业务员说的内容才是"话术" |
| 结构完整（双方都出现） | 0.10 | 不是单方独白 |
| 命中风险词 | −0.35 | 敏感样本不该拿高分 |
| 含价格内容 | −0.10 | 已脱敏，训练价值偏低 |

## 五、与其它项目的咬合

| 方向 | 项目 | 方式 |
|---|---|---|
| 输入 | 项目二 | 客户档案里的真实姓名 → 脱敏词典 |
| 输出 | **项目七** | `feed_conversations()` 供给"已审核成交对话"作为案例素材源（**只有 approved 且 eligible 的对话**；中台没数据时回退旧语料） |
| 输出 | 项目三 | RAG CSV / JSONL 导出 → 陪练题库与质检语料的上游 |
| 输出 | 项目一 / 二 | 知识切片（`knowledge_chunks`）可作为检索语料，导出后入库 |
| 编排 | 项目五 | 以 `data.*` 工具参与编排（**不注册 Agent**：数据层不面向客户对话） |
| 观测 | 项目六 | `/metrics` 暴露 `data_*` 指标族 |

**"不注册 Agent"是刻意的**：数据中台的使用者是数据运营与其他系统，不需要一个"陪聊的 Agent"。为了凑 Agent 数量硬造一个，是反模式。

| 方法 | 路径 | 说明 |
|---|---|---|

| GET | `/staging/{id}` | 单条详情 + 审核流水 |
| POST | `/staging/{id}/review` | `approve` / `reject` / `edit` |

| POST | `/knowledge/build` | 构建切片 + 文章 |

## 七、离线可跑（没有真实微信库怎么验）

```
scripts/seed_data.py  →  生成 .data/data_platform/wechat_source.sqlite
                         （与真实 MSG 库同表结构：message + rcontact）
```

夹具覆盖 9 类边界：高价值成交对话、投诉、垃圾广告、媒体占位、过短、群聊（含发送者前缀）、重复会话。真实适配器 `WeChatSqliteSource` 的要点：

- **只读打开**（`file:...?mode=ro`）：抽取工具不能有写坏别人微信库的可能；
- **列名自适应**（`msgId`/`msg_id`、`createTime`/`timestamp`…），缺关键列时报错并列出已识别列；
- **群消息发送者还原**：内容前缀 `wxid_xxx:\n真实内容`；
- **消息类型占位**：图片/语音/文件转 `[图片]` 等，避免非文本消息被当空内容丢掉。

## 十、高频问答

**Q：真实数据里大部分是垃圾，你怎么保证数据质量？**
> 两个层面：① 入库前用 9 级规则分类，噪声直接丢（本项目实测丢弃率 57%），只让有效对话进暂存区；② 入库后还有人工审核闸门，approved 才算可信数据。并且"进暂存"和"可训练"是两个开关——投诉类对话主管必须看到，但永远不会进训练集。

**Q：三层脱敏怎么证明真的做了三层？**
> 不是靠文档，是靠断言：`verify()` 对已脱敏文本再跑一遍规则，必须返回空；导出前每行都过这个断言，非空整批拒绝。另外脱敏是幂等的，所以"清洗时打过的码"在写入层和导出层不会被二次破坏。

**Q：为什么身份证要先于银行卡脱敏？**
> 18 位身份证同时满足 16-19 位连续数字，如果先跑银行卡规则，身份证会被打成"前 4 + 星号 + 后 4"，既看不出是身份证，审计记录的类型也错了。所以规则带优先级，重叠时身份证赢。

**Q：数据中台为什么没有 Agent？**
> 它的使用者是数据运营和其他系统，不是终端客户，没有"对话"这个场景。我们把它注册成一组 `data.*` 工具参与编排（其中审核是 high risk，必须过 HITL），而不是硬造一个 Agent 凑数。

**Q：审核为什么不能全自动？**

> 错误样本会被模型学走，事后极难归因。所以 approval 是对数据资产的高风险动作，走 HITL：Agent 可以发起，人工必须确认。而且编辑会重置为 pending——改过的内容必须重新审。
