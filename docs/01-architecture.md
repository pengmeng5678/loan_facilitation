# 架构与关键设计决策

本文回答三个问题：**系统怎么分层**、**一次请求怎么流动**、**为什么这么设计**。

---

## 一、分层与依赖方向

```
┌───────────────────────────────────────────────────────────────┐
│ 接入层  FastAPI（/platform · /data · /product · /coaching ·      │
│                   /marketing · /voice · /gateway · /flow）       │
│         也可拆成多个独立服务分别部署                             │
│  项目一 voice_service 额外有一条**外部回调**入口：               │
│         POST /voice/callback/chat ← 火山 RTC 云端（OpenAI 协议） │
│         （音频不经过我们：UDP 走浏览器 ↔ 边缘节点 ↔ 云端 Agent）  │

│   ┌────────────┬────────────┬────────────┬────────────────┐   │

│  LLM(echo / OpenAI 兼容) · Embedding · 向量库(local / Qdrant)     │
```

**关键约束：平台不知道任何业务。** `agent_platform` 里没有一行代码提到"产品""客户""话术""素材""语音"。
业务通过 `AgentCapabilities` 声明能力，平台负责装配。这条约束保证了平台可以承载任意业务 Agent。

**第二条约束：基础设施不知道任何业务。** `gateway`（项目六）里没有一行
`import product_assistant / marketing`。要评测谁，由装配层把调用包装成
`Callable[[EvalCase], dict]` 注入。这条边界有**机器化校验测试**守着。

**第三条约束：流程层不知道其他业务怎么实现。** `flow_ops`（项目八）里没有一行
`import product_assistant / voice_service`：方案初稿调 `plan_provider`、客户档案调 `profile_provider`，
两者由装配层（`app_context.py`）注入。于是它可以只按"状态机 + SOP + 审批"的流程语义演进，
业务项目的接口变化不会传导进来。

**装配方向**：`app_context.py` 是唯一的 Composition Root —— 新增一个 Agent 只改这里：
建服务 → 注册工具 → 注册 Agent 能力函数 →（如需评测）注入评测目标。

## 二、一次请求的完整生命周期

以"业务员让 Agent 生成方案书"为例：

```
POST /platform/agents/product_assistant/run
   │
   ├─1 AgentRuntime.invoke()
   │     · 生成 run_id / thread_id，绑定日志上下文与 Tracer
   │     · 构造初始 AgentState
   │
   ├─2 route 节点        → 意图路由："proposal"
   │
   ├─3 plan 节点         → 计算本轮工具作用域（scoped）
   │     · 只注入 proposal 相关工具 → 工具 schema token 3440 → 225（省 93.5%）
   │     · 写入 state.scoped_tools，记录 token 成本
   │
   ├─4 execute 节点（循环体）
   │     · 预算守卫：步数 / token 超限 → 熔断转人工
   │     · decide()：业务决策（纯函数，HITL 恢复要靠它可重放）
   │     · 若为高风险工具 → ApprovalManager 幂等建单 → interrupt() 挂起
   │     · 否则 ToolRegistry.invoke()：作用域校验 → 参数校验 → 熔断器 → 重试 → 执行
   │     · 写回 tool_calls / observations（Annotated reducer 累加）
   │
   ├─5 critique 节点      → 合规校验：方案书必须生成成功，否则必须已转人工
   │
   ├─6 respond 节点       → 组装结构化输出，落定终态
   │
   └─ Checkpointer 在每个节点后写入线程级快照（可恢复 / 可回放）
```

**意图路由的两种用法**：平台内置 `agent_platform/routing/`（规则 → 向量 → LLM 三级 +
低置信澄清），业务 Agent 目前仍显式使用各自的规则 `route()`（可读、可解释、零延迟）；
三级模块用于需要更高召回或多意图的场景，并配有 72 条评测集与 `scripts/eval_intent.py`。
两条路径并存是刻意的：先把评测基线建起来，再谈替换。

**critique 不是装饰**：`max_critique_rounds` 默认 2，未通过会真的回到 execute 重做；
但**写工具不允许重放**——`executed_write_tools` 命中时只回放上次 observation 并打标记，
避免"打回一次 → 短信发两遍"。

**trace_id 传播**：`agent_platform/tracing.py` 用 `ContextVar` 保存 trace_id，
`Tracer.span()` 自动带上它并写 `span_*_ms` 指标；`RunResult.trace_id` 可直接对外返回。
当前覆盖 platform 与 gateway 的 span，业务包内部的细粒度 span 仍在补。

**HITL 恢复路径**：`POST /platform/runs/{thread_id}/resume`
→ `Command(resume={approved, decided_by, comment})`
→ LangGraph **重放 execute 节点**（因此 `decide()` 必须是状态纯函数）
→ `interrupt()` 直接返回审批结论 → 记录审批留痕 → 继续执行工具。

## 三、十一个关键决策与理由

### 决策 1：为什么选 LangGraph，而不是自己写状态机？

自己写状态机要解决：状态快照、断点恢复、`interrupt/resume`、条件边、子图、并发分支……
这些都是 LangGraph 已经验证过的能力。平台的价值在于**在其之上做业务无关的治理**
（工具生态、预算熔断、审批中心、观测），而不是重造这些基础设施。

> 反面案例（`graph/nodes.py` 注释里也写了）：曾把智能客服全流程做成端到端自主 Agent，
> 结果不确定性太高、成本不可控。教训是 **能用确定性流程解决的，就不要交给 Agent 自由发挥**。

### 决策 2：为什么工具要做"作用域裁剪"（scoping）？

不裁剪时，每轮都要把**全部工具**的 schema 塞进上下文：token 爆炸 + 模型选错工具。
裁剪后按意图只注入相关子集，实测单轮注入的工具 schema token 从全量 **56 工具 ≈3.4k**
降到 **3–7 个工具 ≈0.2–0.4k**（**省 88%–95%，中位 93.5%**）。

同时它还是**安全边界**：不在作用域内的工具，即使被 Prompt 注入也调不动（对应 OWASP LLM06 过度代理防护）。

⚠️ 例外：`escalation` 标签的工具（转人工）**永远可用** —— 逃生舱不能因为裁剪而失效。

### 决策 3：为什么审批请求 ID 要确定性生成？

LangGraph 恢复时会**重放整个节点**。如果每次重放都新建审批单，
审批中心会出现一堆重复待办、指标也会被重复计数。
所以用 `(thread_id, step, tool)` 做稳定哈希生成 `request_id`，并让 `ApprovalManager` 幂等建单。

### 决策 4：为什么拒绝阈值挂在"绝对相关性"而不是"融合分"上？

融合分里的 RRF 部分按 max 归一化后，**排第一名的永远是 1.0** ——
任何"最低分门槛"都会形同虚设，无关问题也会被当成有依据。

因此拒答判据用绝对量：**词项重合度（rerank_score）为主，语义相似度（dense_score）为辅**。
实测（离线 local-hash）：相关问题 rerank ≥ 0.4、无关问题 rerank ≈ 0。
*换成真实 Embedding 后必须重新探测校准。*

### 决策 5：为什么用 RRF 融合而不是分数加权求和？

BM25 的分数是无界的词频统计量，余弦相似度在 [-1, 1] 之间 —— 两者**不可比**，
直接加权会随语料规模漂移。RRF 只用**排名**：`score = Σ 1/(k + rank)`，
天然对分数尺度不敏感，是工业界混合检索的默认做法。

### 决策 6：为什么方案匹配/评分/质检要用确定性代码？

| 场景 | 如果用 LLM | 实际做法 |
|---|---|---|
| 准入判断 | 可能"理解偏差"导致推荐不满足条件的产品 → 客户白跑一趟 + 浪费一次征信查询 | 硬性条件逐条判断，淘汰原因留痕 |
| 合规判定 | 同一次违规，两次判定可能不一致 → 无法审计 | 违规词库 + 正则，结果可复现 |
| 评分 | 偏好长回答、偏好顺从 → 主管不认 | 维度化 rubric + 槽位覆盖度计算 |

LLM 只负责"把结果讲成人话"和"语义层的补充判断"。**业务底线不依赖模型。**

### 决策 7：为什么给每个外部依赖都配"离线实现"？

`EchoLLM` / `LocalHashEmbedding` / `LocalVectorStore` / `InMemorySaver` 让系统
零密钥、零网络即可完整跑通。带来三个直接收益：

1. 新人和 CI 不会被环境问题卡住（clone → pytest → 几秒内通过）；
2. 单元测试不需要 mock 网络，断言的是**真实业务逻辑**；
3. 生产切真实模型时，只改配置，不改任何业务代码。

### 决策 8：为什么"合规"要写成流程约束，而不是一张检查清单？

素材是对外发布的，所以"先审后发"如果在流程上可以被绕过，那张清单就只是自我安慰。
`marketing` 的做法是：**`MaterialGenerator.assemble()` 是产出素材的唯一路径**，
生成即过审；未过审的素材不会被激活计划采用，且 Agent 的 `critique`
会检查"有未过审素材但没有转人工"= 流程不完整。

同理，发送工具**只在需要时进入作用域**（激活路由 + 用户明确说要发），
其余情况下 Agent 手里根本没有这个工具 —— 这比"提示模型不要乱发"可靠得多。

### 决策 9：为什么评测必须"先取基线，再跑本次"？

```
❌ 先跑评测 → 落库 → 再取基线 → 基线就是自己 → gate 永远通过
✅ 先取基线 → 再跑评测 → 与历史比 → 退化超阈值则拦
```

这是这类系统最隐蔽也最致命的 bug：它不报错、不告警，只是让整个门禁变成装饰品。
所以有一条专门的测试（`test_service_gate_orders_baseline_before_current`）锁住这个顺序。

### 决策 10：为什么降级链只能往下退、small 档不配备份？

往上顶（small 失败 → medium）会瞬间打爆成本，而失败原因通常是"上游挂了/配额用尽"，
不是"模型太弱"—— 升档大概率也解决不了问题，只是更贵。
所以 small 档没有后备：要升档必须由调用方**显式**指定 tier，
这样"成本超预期"永远能追溯到一次明确的决定，而不是一次隐式兜底。

### 决策 11：为什么 Redis 锁是 fail-closed，而不是"连不上就降级 SQLite"？

多 worker 部署下，锁的唯一价值就是**跨进程互斥**。Redis 连不上时降级成 SQLite 锁，
互斥范围悄悄缩回本进程 —— 两条请求同时改同一条线索，两边都以为"锁在工作"，
结果是重复建单/重复放款，而且**没有任何报错**。一个明确失败的 503
（"锁服务暂不可用，本次未做任何修改，重试是安全的"）比一个悄悄错误的 200 安全得多。

同一逻辑用在 PG 存根上：`CHECKPOINTER_BACKEND=postgres` 但 DSN 配错时，
启动期直接失败并给出排查指引，绝不回退 memory —— 否则 HITL 恢复会
"看起来正常"地丢状态，排查时连现场都没有。

> 判断标准：**降级之后，系统的安全承诺还剩多少？** 剩不了，就不降。

## 四、并发与扩展

- **`Tracer` 是每 run 重置的实例**：意味着一个 `AgentRuntime` 实例不应被多线程并发复用。
  生产横向扩展的方式是 **多进程 worker + PostgreSQL Checkpointer 共享状态**（见 `docker-compose.yml`），
  而不是在单进程里多线程跑同一个 runtime。这一点在 `observability.py` 注释中显式说明。
- **状态与业务数据分离**：编排状态在 Checkpointer（PG/SQLite），会话与质检数据在业务库（SQLite）。
  多实例部署时编排状态必须走 PG。
- **多 worker 的两条硬约束**（副本数 > 1 时，缺任何一条都会产生"无报错的业务错误"）：
  ① 分布式锁必须换 Redis（`flow_ops/locking.py`）—— SQLite 锁只在本进程内互斥，
  并发改同一条线索会双双拿到锁；② Checkpointer 必须换 PG —— HITL 挂起后 resume
  落到别的副本会取不到状态。两者都 **fail-fast / fail-closed，不静默降级**：
  Redis 不可用 → 503；PG 配错 → 启动失败。
- **水平扩展点**：向量库 → Qdrant；图谱 → Neo4j（替换 `ProductGraph` 实现即可）；
  会话存储 → PostgreSQL（替换 `SessionStore` 实现即可）；锁 → Redis（已内置双后端）。
- **可观测出口**：`GET /metrics`（Prometheus exposition 0.0.4，采集失败也返回 200），
  指标族覆盖 app/runtime/gateway/flow/scheduler 五组，直接对接 Prometheus/Grafana。

## 五、已知边界与后续演进

| 项 | 当前实现 | 生产演进方向 |
|---|---|---|
| 预估通过率 | 基于"准入余量"的启发式 | 用历史放款/拒件数据训练校准模型（保持函数签名不变） |
| Reranker | 词项重合度（确定性、可离线） | bge-reranker / Cohere Rerank 交叉编码器 |
| 文档解析 | 结构化 JSON 政策数据 | 版面分析 + OCR 解析 PDF/表格/扫描件 |
| 客户画像 | 静态 JSON 文件 | 从数据中台实时拉取 |
| 图谱 | 进程内邻接表 | Neo4j（多跳查询与可视化） |
| 会话存档 | 本地 JSONL 语料 | 企业微信会话存档 API 实时回流 |
| 网关缓存 | 进程内字典 + 简单 LRU | Redis（共享缓存 + 自带淘汰策略），多实例部署必需 |
| 成本价格表 | 配置文件里的估值 | 从云厂商账单/价目 API 自动同步 |
| 密钥管理 | 环境变量 + 轮转冷却 | KMS / 密钥托管服务，支持按租户下发 |
| 语义缓存阈值 | 针对离线 local-hash 校准（0.94） | 换真实 Embedding 后必须重新探测校准 |
| 素材效果归因 | 触达流水 + 种子漏斗数据 | 接抖音/小红书/微信数据回流，按素材 ID 精确归因 |
| 素材文案评价 | 规则质量分（结构/渠道/CTA） | 叠加"咨询转化率"做在线学习，让数据决定哪套模板该加量 |
| 语音音色 | 预置音色 + 复刻音色（`voice_type` 切换） | 按业务员批量复刻，客户回拨时听到"上次那个人" |
| 语音打断 | `CancelToken` 在句界退出 | 接入 ASR 中间结果做"预测性停口"（客户刚发出第一个字就停） |
| 语音评测 | 规则判分 + 红线一票否决 | 叠加人工抽检做双盲校准（与项目三 Judge 同一套方法） |
