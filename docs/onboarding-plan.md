# 新人 2 天上手文档体系 · 设计方案

> 目标：新人入职后 2 个工作日，独立熟悉**系统源码、业务逻辑、数据流向**，达到"能讲清、能定位、能改对"的程度。
> 本文是这套文档体系的**设计方案与决策记录**。三个决策点已确认（见第七节），第一批交付物已落地。

---

## 一、先把目标定义清楚：2 天能到哪一步

3.2 万行源码、9 个包、693 个测试，两天"读完"是不可能的。所以目标必须定义成**可验收的熟悉度**，而不是阅读量。

| 层级 | 2 天后应该能做到 | 不要求 |
|---|---|---|
| 能跑 | 独立搭环境、灌种子、跑 demo、启动前后端 | — |
| 能讲 | 不看文档，5 分钟口述一条线索从录入到成交的完整流转，说清每步经过哪个包 | 背诵 API 参数 |
| 能定位 | 给 5 个"我要改 X"，每个 5 分钟内找到文件和函数 | 记住所有文件名 |
| 能改对 | 在不破坏现有测试的前提下完成一个小需求，且没违反七条设计原则 | 独立设计新模块 |
| 知道边界 | 说清 3 个"不能这么改"的反例及原因 | — |

**一句话：两天买到的是"地图 + 指南针"，不是"背下整座城"。**

## 二、现状诊断：9 份文档缺的是什么

现有 `docs/` 共 3374 行，按技术主题组织：

| 文档 | 行数 | 性质 | 新人的困境 |
|---|---|---|---|
| README.md | — | 项目总览 + 七条设计原则 + 八项目介绍 | 信息密度高但埋在开头，新人不会当教材读 |
| 01-architecture.md | 270 | 11 个架构决策及理由 | 讲"为什么"，不讲"从哪读起" |
| 02-getting-started.md | 419 | 环境 + 配置手册 | 教跑起来，没教读懂 |
| 03-api.md | 899 | API 参考 | 手册，两天读不完也不该读 |
| 04–09 各项目 | ~1800 | 每个模块"有什么" | 按模块横切，新人不知道读的顺序和关联 |

**缺的四样东西**：

1. **入口**：没有一份文档说"你现在该读第几页"。
2. **牵引**：没有一条业务主线把 9 个包串起来，新人只能按目录树平铺着读。
3. **反查**：想改某个功能时，没有"业务概念 → 代码位置"的映射，只能靠 grep 碰运气。
4. **验收**：没有自检手段，"看完了"和"看懂了"无法区分。

## 三、核心方法论：五条设计原则

这五条是整个文档体系的灵魂，先定原则再动笔。

### 3.1 由外向内，禁止一上来给目录树

顺序必须是：**先看到系统在跑 → 再理解业务为什么这样流 → 再追数据怎么流 → 最后才看代码在哪**。
新人一打开文档就看到 `src/` 树和架构分层图，会产生"我永远学不完"的挫败感而放弃。

### 3.2 一条业务主线牵引，替代按目录顺序读

用**一条线索从录入到成交**贯穿全程：11 个阶段各读一段相关代码。
新人在任何时刻都知道自己站在业务链路的哪一环，读的每一行代码都有业务含义。
这是本项目最大的优势——11 阶段状态机本身就是天然的教学骨架。

### 3.3 每个声明可验证，文档与代码同源

- 每个结论都带**文件路径 + 行号**（如 `src/flow_ops/workflow.py:412`）；
- 每条命令**复制即可跑**，且给出预期输出；
- 演示数据即教材：11 条线索正好覆盖 11 个阶段，新人可以拿真实数据对照代码，不需要自己造数据。

### 3.4 反例教学，比正例更能划定边界

新人最先犯的错不是"不会写"，而是"在错的层写"——比如把判据写进前端、把幂等键写成随机 UUID、把 Redis 锁降级成 SQLite。
给出 **5 个"看似合理的错误改法 + 为什么错 + 正确位置**，一次讲透，比十条正确规范更有效。

### 3.5 产出驱动，拒绝"我看完了"

每个时间块结束必须有**可见产出**：画一张链路图、口述一段流程、改一个小功能、跑通一个测试。
没有产出的阅读会在四小时后遗忘 80%。

### 4.1 `docs/00-onboarding.md` —— 2 天学习地图（核心）

这是唯一入口，新人只需记住这一个文件。结构：

```
一、如果你只有 10 分钟
   系统是什么（一段话）+ 一张链路图 + 三条最重要的边界
二、Day 1 · 上午：跑起来 + 建立业务全景（09:30–12:00）
   时间块 1（30min）环境与启动 —— 指向 02 第 1–2 节，验收：能打开 /ui
   时间块 2（90min）业务全景 —— 公司业务逻辑 / 11 阶段状态机 / 三角色工作流
   时间块 3（30min）产出：口述完整链路（给评分要点）
三、Day 1 · 下午：追一条线索的数据流（14:00–18:00）
   时间块 4（2h）一条请求的完整生命周期 —— 读 11 第 1–2 节 + 01 第二节
   时间块 5（1.5h）Web 工作台对照 —— 每一屏对应哪个接口、哪个阶段
   时间块 6（30min）Day 1 自检（12 题，过 10 题才能进 Day 2）
四、Day 2 · 上午：源码地图与红线（09:00–12:00）
   时间块 7（1.5h）源码地图 —— 读 10 全文，做 3 次定位练习
   时间块 8（1.5h）七条设计原则 + 五个反例 —— README 第三节 + 01 决策部分
五、Day 2 · 下午：实战（14:00–18:00）
   时间块 9（3h）递进练习 1–5（见 12）—— 其中练习 5 必须做
   时间块 10（30min）Day 2 验收 —— 按 12 的验收单逐项过
六、后续 30 天怎么深入（可选路线图）
```

**每个时间块的固定格式**（这是让文档可执行的关键）：

```
▸ 读什么：docs/xx.md 第 N 节 / src/xxx.py:120-180
▸ 做什么：跟着这条命令跑一遍，对照预期输出
▸ 产出：在纸上画出 X（或向 Mentor 口述 X）
▸ 自检：3 个问题，答不上就回去重读对应小节
```

### 4.2 `docs/10-code-map.md` —— 源码地图

**按业务概念反查，而不是按目录正查**。这是新人最缺的东西。核心是三张表：

**表 A：业务动作 → 代码位置**（约 25 行）

> 定稿见 `docs/10-code-map.md` 表 A，全部锚点经 `scripts/onboarding_check.py --map` 校验通过。
> 下面是定稿前举的几个例子，路径已按校验结果修正：

| 我想改什么 | 去哪个文件 | 关键函数/类 | 顺带要改哪 |
|---|---|---|---|
| 线索阶段的流转规则 | `src/flow_ops/leads.py` | `ALLOWED_TRANSITIONS` | `tests/test_flow_ops.py` 补用例 |
| SOP 超时阈值 | `src/flow_ops/leads.py` | `build_sop_rules()` | `.env` 的 `FLOW_SOP_*` |
| 费用试算公式 | `src/flow_ops/fees.py` | `FeeEstimator` | 测试 + 文档口径 |
| 额度测算的基数口径 | `src/product_assistant/domain/matching.py` | `_INCOME_QUOTA_BASES` | 风险提示文案 |
| 高风险动作白名单 | `src/flow_ops/approval.py` | `high_risk_actions()` | HITL 审批单模板 |
| 内容安全红线 | `src/voice_service/censor.py` | `check()` | 兜底话术回归测试 |
| 幂等键生成规则 | `src/flow_ops/idempotency.py` | `make_idempotency_key()` | 前后端必须同源 |

**表 B：每个包的一页说明**（9 个包 × 每包 12 行）

每包固定六项：**职责一句话 / 入口文件 / 3 个核心类 / 依赖谁 / 被谁依赖 / 不许改什么**。
例如 `gateway`：依赖方向是"被依赖"，**不许 import 任何业务包**（有机器化校验测试守着）——这种边界必须在文档里显式写出，否则新人一定犯。

**表 C：七条设计原则的代码坐标**（README 第三节的"可执行版"）

把每条原则落到具体文件和测试，例如：
> 原则 7「写操作必须幂等、加锁、留痕」→ 看 `flow_ops/idempotency.py` + `flow_ops/locking.py` + `store.py` 的审计四态；守它的是 `tests/test_flow_ops.py::test_*idempotent*`

### 4.3 `docs/11-data-flow.md` —— 数据流主线图解

不讲泛泛的分层，只讲**四条真实主线**，每条用 Mermaid 图 + 逐步文件行号：

1. **AI 对话流**：客户消息 → 网关（路由/缓存/裁剪）→ Agent（工具调用）→ 内容安全 → 落库
   覆盖项目一（语音回调）、二（知识问答）、三（陪练）。
2. **业务流程流**：录入 → 11 阶段状态机 → SOP 扫描 → HITL → CRM/通知 → 审计
   覆盖项目八，这是**全系统最重要的主线**，用种子里一条真实线索（如孙丽娟）走完。
3. **数据中台流**：原始对话 → 分类 → 脱敏 → 审核闸门 → 导出/知识切片
   覆盖项目四，重点讲"审核必须人点"和 `keep` 与 `dataset_eligible` 为什么必须分离。
4. **素材与激活流**：模板 → 合规先审后发 → 脱敏 → 渠道语感 → 防骚扰 → 归因
   覆盖项目七。

每条主线末尾给一个**"跟着跑"的命令**（`python scripts/demo.py` 的对应段或 curl 链），让新人亲眼看到数据在表里变化。

### 4.4 `docs/12-self-check.md` —— 自检与验收

**20 道自检题**（Day1 末 12 题 / Day2 末 8 题），题目必须是**可判定的**，不是问答题：

- 差：'讲讲状态机'（无法判断对错）
- 好：'一条线索能从「已邀约」直接跳到「已成交」吗？在哪段代码被拦住？如果业务要允许，改哪里？'
- 好：'房产抵押贷的额度为什么不能乘月收入？相关常量叫什么？漏了会怎样？'

**5 个递进练习**（难度递增，都给了验证方式）：

| # | 练习 | 涉及层 | 验证 |
|---|---|---|---|
| 1 | 给一个新阶段加一条流转规则 | 领域层 | `pytest tests/test_flow_ops.py -k transition` |
| 2 | 调整一个 SOP 阈值并观测预警变化 | 服务层 + 配置 | 重灌种子，预警条数符合预期 |
| 3 | 给某个包加一个工具并注册 | 平台层 | `/ready` 工具数 +1 |
| 4 | 加一个只读 API 端点 + 前端调用 | 前后端联调 | `tsc` 0 错 + 页面显示 |
| 5 | 完整走一遍"改需求 → 改代码 → 补测试 → 更新文档" | 全链路 | 693 个测试仍全绿 |

**验收单**（Mentor 签字用）：第五节那五项，每项给了"通过标准"。

### 4.5 入口改造（README.md）

加一节「**新人入职从这里开始**」，三行字 + 一个链接指向 `docs/00-onboarding.md`。
同时把 README 第三节"七条设计原则"标注为"Day 2 上午精读"，让新人知道它不是背景资料而是必读教材。

## 六、写作规范（防止文档腐烂）

文档写出来那天就开始过期，必须用纪律对抗：

1. **行号引用要带提交号**：`src/flow_ops/workflow.py:412` 这种写法一改代码就失效。改为引用**函数名 + 文件**（`workflow.py 的 execute_approved()`），并在文档头部注明"代码锚点以函数名而非行号定位"。
2. **所有命令必须实际跑过**：写文档的人按文档从零走一遍，跑不通的命令不许写进去。
3. **数字必须有出处**：11 阶段、56 工具、693 测试这类数字，标注取数命令（如 `pytest --collect-only`，注意别重复传 `-q` 否则摘要行被抑制），不要手抄。
4. **每次新增项目/模块，同步更新 10-code-map 表 B**：把这条写进 CONTRIBUTING 或提交规范。
5. **自检题的答案不写进文档**（或放附录折叠）：新人对不出答案时会直接看答案，自检就失效了。

## 七、落地计划与工作量

分两批，第一批就能解决 80% 的问题：

| 批次 | 内容 | 预估 | 优先级理由 |
|---|---|---|---|
| **第一批** | `00-onboarding.md` + `10-code-map.md` + README 入口 | 3–4h | 这两份直接决定新人第一天下班时的状态 |
