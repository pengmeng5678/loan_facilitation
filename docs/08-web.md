# Web 工作台（TypeScript + Vite + React）

`web/` 是助贷 AI 中台的业务工作台：把七个服务的核心流程收进一个单页应用，
业务员/主管打开浏览器就能完成日常操作，不需要对着 curl 文档敲命令。

- **技术栈**：TypeScript 5.6（strict）+ Vite 5.4 + React 18.3，零 UI 框架依赖（纯 CSS）
- **两种跑法**：dev 模式（Vite dev server + API 代理）与生产模式（构建产物由 FastAPI 服务于 `/ui`）
- **设计主线**：前端只做"展示与触发"，**所有业务判据都在后端**（状态机、SOP、审批门、
  脱敏、费用口径）—— 前端没有任何一条" if 阶段==xx 就显示 yy "的业务规则副本。
- **使用者是销售业务员**：界面上不出现 `rep_01`、`first_call`、`ok/blocked` 这类机器键，
  全部翻译成人名、动作名、中文结果（翻译表集中在 `src/hooks.ts`）。

## 一、页面清单与导航

左侧导航按**业务员一天的使用顺序**分组，不按技术模块分：

| 分组 | 页面 | 覆盖流程 | 关键交互 |
|---|---|---|---|
| 工作台 | 今日工作台 | 今天该干什么 | 超时线索横幅 → 待办三档（超时/审批/首呼）→ 阶段分布 → 最近动态（审计流水，谁在什么时候动了哪条线索） |
| 客户 | 我的客户 | 线索从进来到成交 | 6 列看板（待分配 → 待首触 → 跟进中 → 已邀约 → 到店推进 → 已成交）+ 列表视图；卡片上的「下一步」就是唯一正确操作；已流失单独收在底部一条 |
| 成交支持 | 方案中心 | 客户资质 → 产品准入 | 选客户自动出方案：主力方案 + 命中理由 + 风险提示 + 备选 + 被淘汰产品及原因 |
| 成交支持 | 审批中心 | HITL 高风险动作 | 两段式：批准（只表达"允许"）→ 执行（才真的发出去）；三档视图：待我审批 / 已批准待执行 / 全部 |
| 客户服务 | 客户查进度 | 客户问「到哪一步了」 | 线索 + 手机后 4 位双因子校验，右侧手机壳直接演客户那一屏（脱敏视图由服务端保证） |
| 客户服务 | 跟进预警 | 漏跟进兜底 | 两级（超 2×SLA 立刻处理 / 刚超时还能救）、认领、手动扫一遍 |
| 管理 | 团队看板 | 主管视角 | 累计口径漏斗（每段比上一段少的人就是卡在这一段）、漏跟进率、流程健康度、部署形态 |
| 管理 | 数据资产 | 对话 → 语料 | 抽取 → 9 级分类 + 三层脱敏 → 人工审核闸门 → 四格式导出 |

**抽屉（客户详情）**是业务的真正执行面：一个阶段只突出一个主按钮
（`arrived` → 生成准备包、`proposal_ready` → 费用试算、`fee_estimated` → 确认费用并签约），
其余动作收在「其他操作」里。四个 tab：概览 / 方案 / 到店准备 / 记录。

### 1.1 界面语言的翻译约定

后端是给机器看的，界面是给人看的，两者**不是同一套词**。翻译只在前端做一层，
且集中在一处（`src/hooks.ts`），不散落在各页面：

| 机器侧 | 业务员看到 |
|---|---|
| `stage=first_called` | 已首呼（下一步：添加微信） |
| `action=first_call / add_wechat` | 打首呼 / 加微信 |
| `owner=rep_01` | 张晓东 |
| `actor=seed / agent` | 系统 / AI 助手 |
| `result=ok / blocked / idempotent_hit` | 成功 / 被拦截 / 重复点击已拦截 |
| `readiness.build` 的 `准备包 pk_xxx：方案=X 费用=20000.0 耗时 0ms` | 生成到店准备包 · 主推 X · 服务费 ¥2 万 |
| `lock_backend=RedisLockBackend` | Redis（可多副本） |

工程指标（生成耗时 P95、评测分数线）**不放在业务页面**：业务员看不懂，
技术同事去 `/metrics` 与 Golden Set 报告里看，两条线不混着讲。

### 1.2 手机端（业务员的真实设备）

业务员不在工位上：在门店门口、在车里、在客户对面，掏出来的是手机。
所以 760px 以下不是"把桌面缩小"，而是换一套交互：

| 项 | 桌面 | 手机（≤760px） | 为什么 |
|---|---|---|---|
| 导航 | 左侧深色分组侧栏（232px） | 底部 5 格 tab：今日 / 客户 / 方案 / 审批 / 更多 | 390px 宽的竖侧栏只能缩成一列看不懂的图标；底部是拇指够得到的位置 |
| 顶部栏 | 标题 + 副标题 + 业务链路 + 身份切换 + 预警 | 只剩标题 + 预警铃 | 身份切换和"业务链路"收进「更多」面板 |
| 客户页默认视图 | 看板（6 列一屏看全流程） | 列表（客户 / 阶段 / 停留 / 打开） | 看板在手机上要滑 6 屏找一个人；列表把"等多久"和"打开"放在一屏 |
| 固定多列 | 2/3 列并排 | 一律单列 | 并排会把中文压成逐字竖排 |
| 指标卡 | 自动铺满一行 | 固定 2 列 | 一张卡占满屏等于没有总览 |
| 进度条（10 步） | 等分 | 横滑，每步 58px | 等分后每步 32px，标签被截成"新…待…" |
| 查进度页的"手机壳" | 模拟客户手机 | 脱掉外壳直接铺满 | 业务员本人就拿着手机，再套一层壳是浪费屏幕 |
| 输入框 | 13–14px | 16px | iOS 对字号 <16px 的输入框会在聚焦时放大整页 |

这一节里有四条是**踩过的坑**，改之前先看：

1. **`overflow-x: auto` 会连带裁掉垂直方向**。漏斗横滚一次之后，柱子上方的数字
   直接不见了 —— 因为 `overflow-x: auto` 会把 `overflow-y: visible` 算成 `auto`。
   所以漏斗在手机上保持等分、隐藏第二行「占比 · 卡住」，不横滚。
2. **inline style 覆盖不过媒体查询**。抽屉宽度原来是组件内联
   `style={{ width: "min(720px, 96vw)" }}`，手机上怎么改都留一条缝露出底下页面；
   现在宽度通过 CSS 变量 `--drawer-w` 传给 `.drawer`，窄屏一句 `width: 100%` 就够。
   同理，页面里的 `gridTemplateColumns` 全部换成语义类（`.g-2` / `.g-3` / `.g-split` /
   `.g-side` / `.g-kpi`），窄屏才能统一收成一列。
3. **`1fr` 的下限是 `auto`**，长手机号 / 长产品名会把列撑破，整页横向溢出。
   所有网格列都写成 `minmax(0, 1fr)`。
4. **底部悬浮条会盖住抽屉操作条**（`.overlay` 原来是 `z-index: 50`，和 tab bar 同层且更靠前），
   抽屉里的「关闭 / 推进」按钮会被 tab 压住 —— overlay 已提到 55。

对应的验证是机器化的（不是肉眼）：`web/src` 下四档宽度 × 8 个页面逐页断言
「无横向溢出 + tab bar/侧栏显隐正确 + 控制台 0 报错」，宽度取 390 / 768 / 1024 / 1440。

### 1.3 演示数据（`scripts/seed_data.py`）

演示数据是为了让**每一屏都有真实业务场景**，不是为了填满控件：

- 11 条线索**覆盖 11 个阶段各一条**，看板 6 列全部有卡片，漏斗每段都有真实差值；
- 其中 1 条首呼逾期 165 分钟（超 2×SLA，需立刻处理）、1 条加微逾期 25 分钟
  （刚超时，还能救）—— 预警页的两级分级才有对照；
- 4 张审批单覆盖三态：待审批 ×2 / 已批准待执行 ×1 / 已执行 ×1（批准 ≠ 已执行）；
- 11 位客户档案覆盖公积金 / 社保 / 执照 / 房产 / 保单 / 车产各类资质，其中
  1 位负债比接近上限（匹配结果会给出"负债比临界"的风险提示）；
- 时间轴按真实节奏摊开（首呼 → 加微 → 跟进 → 邀约次日到店 → 出方案 → 算费用），
  落在 09:00–21:00 之间，不会出现"凌晨 5 点打电话"这种一眼假的数据。

种子**可重复执行**：线索录入走业务幂等键，重复跑不会产生重复线索；
`_spread_timeline()` 只在夹具层把时间轴摊平（脚本直连 SQLite 改 ts），
生产代码里没有任何"改审计时间"的入口 —— 能改的审计就不叫审计。

### 1.4 API Key 门

后端开启 `API_AUTH_ENABLED` 时，首屏会用 `/health`（白名单，无需 Key）之后
的第一次业务请求（`/flow/stats`）探测鉴权状态：

- **401** → 顶部弹出 Key 输入框，填入 `API_AUTH_KEYS` 中任意一把即可；
- **网络错误 / 后端没起** → 不当成鉴权问题，各页面自己显示错误（"连接不上后端"和
  "Key 不对"是两回事，混在一起排查成本极高）。

Key 只存在浏览器 `localStorage`，不上送任何第三方；`清除` 按钮一键移除。

### 1.5 幂等键按业务语义生成

所有写操作（录入线索、推进阶段、创邀约……）都带 `Idempotency-Key` 头，
**按业务语义拼接**（如 `intake:{customer_id}:{source}:{工号}`），不是随机 uuid：

- 随机 uuid 防不住"用户重复点击 / 网络重试 / 刷新再提交" —— 每次都是新键，
  后端幂等形同虚设；
- 业务语义键与后端 `flow_ops/idempotency.py` 是同一个道理：同一客户同一来源
  同一时间段的重复提交，返回的是**当前状态**（客户想知道"我的线索到哪了"），
  不是一条重复记录。

## 二、两种跑法

### 2.1 dev 模式（前端开发）

```bash
cd web
npm install        # 首次（或 package.json 变更后）
npm run dev        # → http://localhost:5173
```

`vite.config.ts` 把 10 个前缀（`/platform` `/product` `/coaching` `/marketing`
`/gateway` `/voice` `/flow` `/health` `/ready` `/metrics`）代理到
`http://127.0.0.1:8000`：

- 前端代码里**不出现任何后端地址**，也就不存在跨域（同源代理）；
- 后端独立重启不影响前端 HMR，反之亦然。

> **Windows 两个坑（都已写进配置注释）**：
> ① 代理目标与 dev server 都写 `127.0.0.1` 不写 `localhost` —— Node 17+ 对
> `localhost` 的解析顺序变成字面序，IPv6 `::1` 排在 `127.0.0.1` 前面，
> 于是"后端起着、代理却 connection refused"（vite 只监听 `[::1]` 时，
> 按 IPv4 访问的客户端全部连不上）；
> ② `base: "/ui/"` 必须与后端挂载路径一致，否则构建后 JS/CSS 全 404
> （典型的"本地好的、上线白屏"）。

### 2.2 生产模式（一个端口全都有）

```bash
cd web && npm run build     # 产物到 web/dist
# 重启后端（保持 uvicorn --app-dir src agent_platform.api.app:app）
```

FastAPI 启动时检测 `web/dist` 存在即挂载 `StaticFiles(distan, html=True)` 到
`/ui`（`src/agent_platform/api/app.py:_mount_web_dist`）：

- 部署包**不需要 Node**，后端一个进程服务 API + 前端 + 文档；
- 没有 dist 目录时 `/ui` 不存在，其余功能完全不受影响（本地纯后端开发无感）；
- 首页路由 `/` 会带上 `"web": "/ui"` 字段告知前端挂载点。

## 三、目录结构

```
web/
├── package.json          # react 18.3.1 + vite 5.4.11 + ts 5.6（零运行时框架依赖）
├── tsconfig.json         # strict + noUnusedLocals（构建即类型检查）
├── vite.config.ts        # base:/ui/ · host:127.0.0.1 · 10 前缀代理
├── index.html
└── src/
    ├── main.tsx          # 入口
    ├── App.tsx           # hash 路由 + KeyGate 首屏探测 + 侧栏分组
    ├── api.ts            # 全部端点类型化封装 + ApiError + Key 头 + 幂等键
    ├── hooks.ts          # useAsync / 阶段-渠道-人员翻译表 / 审计人话翻译 / 格式化
    ├── styles.css        # 纯 CSS（无 UI 框架）：设计令牌 → 组件 → 响应式三段
    ├── components/       # Shell（桌面侧栏 + 手机底部 tab + 更多面板）
    │                     # LeadDrawer（客户详情四 tab）/ StageRail（11 阶段→10 步进度）
    │                     # ui.tsx（设计系统：Card/Button/Badge/Drawer/Modal/Field…）
    └── pages/            # Today / Customers / Solution / Approvals / Alerts / Progress / Team / DataAssets
```

`styles.css` 里的 `.g-2 / .g-3 / .g-split / .g-side / .g-kpi` 是**布局语义类**，
不是工具类库：它们存在的唯一原因是「窄屏要能把并排改成一列」，
而 inline 的 `gridTemplateColumns` 覆盖不过媒体查询。新页面要并排就套这些类，
不要写内联 grid。

`api.ts` 是唯一与后端契约对齐的地方：每个函数对应一个端点，请求/响应都有
TypeScript 类型。后端改字段这里立刻编译报错，不会流到运行时才发现。

`hooks.ts` 是唯一与后端**语义**对齐的地方：阶段键、动作键、人员工号、
审计动作名到中文的映射全在这里，页面只调用 `stageLabel() / actionLabel() /
ownerLabel() / auditText()`，不自己拼字符串 —— 否则同一个 `first_call`
在三个页面会出现三种译法。

## 四、联调验证（机器化证据）

`tests/test_web_contract.py` 是**真 HTTP 联调**，不是 TestClient 进程内调用：

1. 起一个随机空闲端口上的 uvicorn 子进程（数据目录全部指向临时目录，
   `API_AUTH_ENABLED=true` + 一把测试 Key），先跑 `seed_data.py` 灌数据，
   轮询 `/health` 就绪（60s 上限）；
2. `test_full_business_flow_over_http` 打 **14 步业务全链路**：
   无 Key 401 → 带 Key 200 → `/flow/stats` 看锁后端 → 录入线索（幂等键）→
   重复提交命中缓存 → 推进状态机（非法流转 409）→ 创邀约 → 确认到店 →
   到店前一页纸 → 费用预估 → HITL 申请/批准/执行（未审批直接执行 409）→
   自助查询（正确后 4 位 200 / 错误 403）→ SOP 扫描 → 产品问答 →
   `/metrics`（Prometheus 格式）→ `/ui`（前端挂载）；
3. 第二个用例守接口形状（错误码、脱敏、白名单）。

```bash
pytest tests/test_web_contract.py -v    # 2 passed
```

## 五、多 worker 部署时前端要知道的事

前端本身**无状态**（Key 在 localStorage，其余全来自 API），可以任意水平扩展。
但它展示的部署形态来自后端，多 worker 时确认两件事：

1. `/flow/stats` 的 `lock_backend` = `RedisLockBackend`（不是就说明锁还在用
   进程内 SQLite，多副本互斥失效）；
2. HITL 审批在副本 A 挂起、副本 B resume 能恢复（`CHECKPOINTER_BACKEND=postgres`）。

配置与原理见 README「多 Worker 部署」一节与 `docs/07-flow-ops.md` 第九节。
